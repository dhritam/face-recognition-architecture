Repository architecture / 2026.10

One image in.
One decision out.

An open-set face recognition server. InsightFace produces normalized 512-dimensional vectors, FAISS retrieves candidates, and the database (SQLite locally, Postgres on Supabase in production) remains the canonical record of people, templates, settings, visits and operational events. Around that core sit operator login, attendance, visitor management, alerts and short-lived search sessions.

Decision output is a cosine similarity — never a probability.

01 / System map

Runtime architecture

One uvicorn worker owns one lazily composed object graph (app/container.py). The lifespan warms it before serving, so models, repositories, policies, the in-memory index and the background sweepers are stable across request threads. In production the process runs in Docker on a GCP VM behind nginx, with OpenVINO as the first execution provider.

02 / Frontend + backend

Application boundaries

The repository has three user-facing clients and one primary recognition backend. They share the generated OpenAPI contract, but each client owns a different amount of capture and presentation logic. The Next.js server is a security-preserving proxy, not the system of record.

Respond, then record

Single worker

04 / End-to-end flow

Application flow diagram

This diagram follows a request from capture or operator action to the immediate response, then separates durable writes and best-effort work that continues after recognition has answered.

Latency boundary: image decoding and model work happen before the response. Recognition-event rows, snapshots and alerts happen afterward, so a slow remote database or email provider does not add to the recognition decision time.
05 / Cache database

Derived state and cache database

Production uses several deliberately separate accelerators. None replaces the canonical Postgres database. The item commonly called the “cache DB” is a selective SQLite metadata replica on each API instance—not Redis and not a backup.

Metadata replica synchronization
Source of truth

Postgres

Canonical persons and embeddings writes commit in the recognition schema.

Ordered feed

replica_changes

Postgres triggers append table, row key, operation and sequence for person/template mutations.

Background poller

Synchronizer

Every 2 s, consumes ordered batches of up to 500 and applies idempotent upserts/deletes.

Per instance · local disk

/data/metadata/replica.db

WAL SQLite with people, embedding display metadata and its last applied sequence.

API reads use the replica only while ready; otherwise the repository immediately reads Postgres
Startup

Validate and rebuild

Integrity failure, an uninitialized file or an impossible cursor causes a repeatable-read snapshot rebuild before the cache becomes ready.

Read after write

Catch up immediately

After successful API mutations the middleware asks the replica to consume the feed; failure never rolls back the canonical write.

Failure mode

Disable and fall back

Sync errors mark the replica unready, use Postgres for reads, and retry with bounded backoff up to 30 seconds.

What replica.db never stores

  • Face vectors or FAISS search data
  • Passwords, credentials or sessions
  • Access, unknown-face or audit events
  • Visits, alerts or runtime settings
  • Thumbnail or snapshot bytes
Operational rule: keep one replica file per API instance on local persistent disk. Never share it over a network filesystem, restore it as a backup, or promote it to canonical storage.
06 / Signal paths

Request flows

The same core services serve dashboard, console, CLI, webcam, mobile, kiosk and edge callers. Choose a trace to see where inference, policy, persistence, and logging occur.

Open-set 1:N recognition

POST /api/v1/recognize finds every face (or the largest max_faces), evaluates it, and searches the gallery. Matching requires quality policy, liveness policy, an active person and the calibrated threshold to all pass.

READ · WRITE AFTER RESPONSE
01

Take a slot

Inference slot (503 after 2 s); byte and pixel limits on decode.

02

Detect faces

SCRFD boxes, landmarks and scores; smaller detector for crops.

03

Analyze

Quality and liveness; demographics and expression unless attributes=false.

04

Embed & search

Normalized (512,) vector; top search_k templates grouped per person.

05

Decide

Threshold → match / unknown; disabled people never match.

06

Respond, then log

Background task: access or unknown row, snapshot, alerts.

No configured match threshold means every face is UNKNOWN. source=live unknown faces are held per track and written once (after 2 s, or when the track ends), and dropped if the track later matches. A remote database adds nothing to recognition latency.

Transactional enrollment

POST /api/v1/persons accepts multiple source images, but each must contain exactly one usable live face. Duplicate findings are reported and queued for review, never merged.

CANONICAL WRITE
01

Validate each image

Exactly one detected face is required.

02

Gate quality

Reject size, blur, exposure, pose or confidence failures.

03

Gate liveness

When liveness is on, spoofs never progress.

04

Check duplicates

POSSIBLE_DUPLICATE opens a duplicate_reviews row.

05

Person, email, group and embeddings in one transaction.

06

Add stable IDs, save index, then audit with the actor.

If the index update fails after the database commits, enrollment removes the committed rows and re-raises. Opt-in thumbnails and face profiles may fail without invalidating stored templates.

Claimed-identity 1:1 verification

POST /api/v1/verify compares the largest face directly with that person’s stored templates and does not depend on FAISS.

DIRECT DATABASE READ
01

Resolve person

Load claimed identity and templates.

02

Pick the face

No face produces a domain error.

03

Assess

Quality and liveness apply the same policy gates.

04

Produce a normalized query vector.

Max cosine similarity across claimed templates.

Threshold match (never for a disabled person); log access on success.

Verification is 1:1: it writes no unknown-face event, captures no snapshot and raises no alert. Recognition and verification share the live threshold service.

Split edge / server inference

The device detects, evaluates, and embeds locally. POST /api/v1/match transports no image — only the model name, normalized embeddings, quality verdicts, and liveness results. It is the one route that needs no operator session.

TRUST BOUNDARY

Quality and optional liveness run on device.

03

The server owns policy. An edge-supplied liveness score is evidence, not the final verdict; when server liveness is on, every face must provide it. Embeddings are accepted in requests only, never returned.

Operator face login

POST /api/v1/auth/face-login turns one live face into a session token. With require_session (prod), every other route except /match needs Authorization: Bearer as well as the API key.

SESSION ISSUE
01

Rate-limit

Failed attempts per client IP; audited with a reason only.

02

One face

Exactly one face that passes quality.

03

Always liveness

Checked even while the global switch is off.

04

Match

Match threshold, or min_similarity if stricter.

05

Admin gate

Active person in auth.admin_group.

06

HMAC-SHA256 v1.payload.sig; refresh rotates it.

Every request re-reads the person (cached), so disabling someone or moving them out of the admin group ends their sessions. Logout revokes one token; logout-all revokes every token issued before now. Email/password login and reset links issue the same session under the same rule.

Visitor kiosk check-in

POST /api/v1/visits/kiosk?mode=in|out|auto recognises a frame and moves the matched visitor’s visit along. Visitors are ordinary people in group Visitors plus a visits row naming their host.

Targeted search & photo sorting

POST /api/v1/reference-sets keeps the largest face of each reference photo; /reference-sets/{id}/recognize then returns only faces in a frame that match those references. Photo sorts group the faces of many photos by person.

07 / Invariants

Rules the design protects

These are system invariants, not incidental implementation details.

VECTOR/01

Validated embeddings only

Every stored, indexed, or transported vector is normalized float32 with shape (512,).

DECISION/02

Uncalibrated means unknown

A null match threshold never accepts an identity. No production threshold is hard-coded.

IDENTITY/03

Stable ID mapping

AUTOINCREMENT / identity embedding IDs are never reused and are also the FAISS vector IDs.

PRIVACY/04

Minimize retained data

Responses never expose embeddings; logs never hold images, embeddings, demographics, or expression.

MATCH/05

Similarity, not confidence

Scores are cosine similarities shown as Similarity: 0.xxx, never percentages.

DUPLICATE/06

Report, never merge

Possible duplicates return POSSIBLE_DUPLICATE and open a review; resolving changes no person.

INDEX/07

Derived and repairable

Startup compares database IDs with FAISS IDs and rebuilds the projection on any mismatch.

FAILURE/08

Recognition keeps serving

Event, snapshot and alert writes run after the response and never raise.

OPT-IN/09

Biometric extras are switches

Thumbnails, snapshots, face profiles and per-event estimates are all off by default.

MEMORY/10

Search sessions stay ephemeral

Reference sets and photo sorts live in process memory only and expire.

AUTH/11

Sessions follow the person

Disabling an operator or changing their group ends their sessions on the next request.

SECRET/12

Secrets stay server-side

Mailjet keys, the Supabase secret key and the session secret are never returned or logged.
